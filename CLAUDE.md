# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

PaCo is a macOS (14+) parental control app: internet on/off scheduling via `pf` firewall, app restrictions, usage tracking, and a child→parent time-extension request/approve workflow over Bonjour. See README.md for full architecture, installation, and state-reset instructions.

## Commands

The Xcode project is **generated by XcodeGen from `project.yml`** — never hand-edit `PaCo.xcodeproj`. After adding/removing source files or changing targets:

```bash
xcodegen generate
```

```bash
make build            # Debug build (scheme PaCo)
make build-release    # Release build into build/DerivedData
make pkg              # Release build → installer pkg at build/PaCo-<VERSION>.pkg
make clean            # rm -rf build/
make clear-pin        # Delete stored PIN hash+salt from Keychain (testing)

# Tests (separate scheme)
xcodebuild test -project PaCo.xcodeproj -scheme PaCoTests -configuration Debug

# Single test class / method
xcodebuild test -project PaCo.xcodeproj -scheme PaCoTests \
  -only-testing:PaCoTests/ScheduleEvaluatorTests/testSomething
```

## Architecture

One Xcode project, four targets:

- **PaCo** (`PaCo/`) — SwiftUI `MenuBarExtra` app (`LSUIElement`), runs as either Parent or Child role chosen at onboarding (`AppState.mode`: onboarding/parent/child). SwiftData persistence.
- **PaCoDaemon** (`PaCoDaemon/`) — root LaunchDaemon; owns the `pf` anchor `com.paco` and process killing. Reached from the app via XPC (`DaemonXPCClient` ↔ `DaemonXPCProtocol` in PaCoShared).
- **PaCoAgent** (`PaCoAgent/`) — user LaunchAgent; 30-second schedule tick (most-restrictive-wins, optional grace period), NSWorkspace app monitoring, usage tracking.
- **PaCoShared** (`PaCoShared/`) — local Swift package all three link against: SwiftData models, XPC protocol, Codable transfer types, PIN/Keychain, `ScheduleEvaluator`, `PaCoFiles` (shared JSON paths).

### Communication (three distinct channels)

1. **App ↔ Daemon:** XPC (internet toggle, kill process). Connection is validated by bundle identifier.
2. **App ↔ Agent:** JSON files in `~/Library/Application Support/com.paco/` (`schedules.json`, `restrictions.json`, `config.json` written by app; `usage.json`, `events.json` written by agent/child app). The app watches `usage.json` and `events.json` with `DispatchSource` file watchers set up in `PaCoApp.swift`; `SyncManager` handles serialization.
3. **Parent Mac ↔ Child Mac:** Bonjour/TCP (`BonjourService`) carrying `PaCoMessage` commands (e.g. `.requestExtension`, `.approveExtension`).

The time-extension flow crosses all of these: child writes a `NotificationEvent` to `events.json` + sends Bonjour message → parent's events watcher inserts a `TimeExtensionRequest` into SwiftData (deduped by event id via `EventTracker` and by request id) → approval toggles internet via XPC and replies over Bonjour.

### Things that are easy to get wrong

- **New SwiftData model?** It must be added to the `Schema([...])` list in `PaCoApp.swift`, and models live in `PaCoShared/Sources/PaCoShared/Models/`.
- **PaCoTests links only PaCoShared** (see `project.yml`) — logic that needs unit tests must live in the PaCoShared package, not in the app/daemon/agent targets.
- In `PaCoApp.onAppear`, `determineMode(context:)` must run before the child-mode Bonjour advertising check — ordering is documented in a comment there.
- `SWIFT_STRICT_CONCURRENCY` is `minimal` on all targets.
- Full end-to-end daemon/agent testing requires Developer ID signing (`SMAppService`/XPC mach services enforce it); unsigned builds run the UI but daemon/agent connections fail.
